1.What This Project Is

Global Alert (internally also called GEWS/MHEWS — Multi-Hazard Early Warning System) is a platform that disaster-management authorities use to do three things: see what hazards are happening right now anywhere in the world, understand who and what is actually at risk from a given hazard, and act — draft, approve, and send an official, standards-compliant public alert through email, WhatsApp, and a public web portal.

It is built to be handed over, country by country, as a self-contained product: each country's disaster agency gets its own administrators, its own users, and — eventually, once the setup wizard described in Section 3 is built — its own independently hosted copy of the entire system.

2.How the System Works — Architecture & Data Pipeline

The system has three moving parts working together at all times: a set of automated data collectors, a central database that everything reads from and writes to, and the map/admin application that a human actually uses. Nothing here requires manual data entry to function — hazard events flow in on their own, continuously.

2.1 — Data flows in from real, independent sources

Live hazard feeds
USGS, EMSC, AFAD, Kandilli, GEOFON (earthquakes) · NASA FIRMS (wildfire) · GDACS (multi-hazard) · WHO / PTWC / FEWS NET (epidemic, tsunami, food security)
→
Aggregator service
Always-on background process. Normalizes every source into one common event shape, removes duplicates (e.g. two agencies reporting the same quake), and stores the result.
→
Database
Supabase (PostgreSQL + real-time updates). Every connected map updates the instant a new event is written — no page refresh needed.

A country's disaster agency can also add its own additional data source at any time from the admin panel — no engineering work required — and the same pipeline picks it up automatically.

2.2 — Context layers: what's actually on the ground

A hazard event on its own only says "something happened here." To answer "who is affected," the system separately (and independently of the live hazard feeds) imports real-world context data for each served country and keeps it ready on the map:

LayerReal sourceWhat it answers
Population densityWorldPop, Meta/HDX, GHSL (three independent population datasets)How many people live near this hazard?
Critical infrastructureOpenStreetMap (schools, clinics/hospitals, emergency services)Which specific facilities are nearby, filterable by category
General building densityMicrosoft's global building-footprint datasetHow dense is construction in this area? (~128,000 measured cells for Turkey alone)
Rivers & watershedsHydroRIVERS / HydroBASINS, GloFAS river dischargeFlood/liquefaction exposure near water
Terrain steepnessCopernicus satellite elevation dataLandslide-susceptible zones after an earthquake
Rainfall & drought indicatorsCHIRPS rainfall, vegetation/soil-moisture anomaly indicesDrought and food-security risk trends

These imports run as separate, independent background jobs (Docker containers) — they can be re-run per country at any time to refresh the data, without touching the live hazard-monitoring pipeline at all.

2.3 — Turning data into a decision: the cascading-risk engine

A defining feature of this system is that it can flag secondary risks a hazard creates — e.g. "this earthquake is close enough to a river that liquefaction-driven flooding is plausible," or "terrain steepness near this epicenter suggests landslide risk." This is done with simple, transparent, admin-editable rules ("if magnitude ≥ X and distance to Y ≤ Z km, then flag risk category W") — deliberately not a machine-learning model. Every triggered recommendation can be traced back to the exact rule and threshold that produced it, which matters a great deal for an external body auditing the system's reasoning (e.g. a UN partner reviewing methodology).

2.4 — From detection to public alert

Detected event
Real hazard on the live map, or a manually reported community incident
→
Draft alert (CAP)
Operator drafts a standards-compliant (OASIS CAP v1.2) public warning
→
Four-eyes approval
A second, separate approver must sign off before anything goes out
→
Dispatch
Email, WhatsApp, and a public web portal — with automatic retry and delivery tracking

Every step above — every login, edit, approval, and dispatch — is written to a tamper-evident audit log (a cryptographic hash chain, the same integrity idea used in blockchains), so the full history of any alert can be reconstructed and verified later.

3.What Happens Next: The Federated Setup Wizard

Today, every served country (Turkey, Madagascar, Malaysia) runs on one shared, centrally-hosted system that we operate — already fully separated by country (a Turkey administrator cannot see Madagascar's private data, and vice versa; this isolation is already built, tested, and running in production). The next stage of the project is letting each country instead run its own, fully independent copy — its own server, its own database, full data ownership — for organizations that require this for sovereignty or compliance reasons.

3.1 — What already exists and will not need to be rebuilt

  • The secure user-invitation system (a new user gets a one-time secure email link to set their own password — the same industry-standard mechanism used by major cloud platforms).
  • The four-tier role hierarchy: Super Admin → Country Admin → Org Admin → Viewer, where a Country Admin can only invite/manage users within their own country, and so on down the chain.
  • Self-service onboarding of a brand-new hazard type (e.g. "landslide") from the admin panel, with zero engineering work required.

3.2 — What still needs to be built

  1. The installer/setup wizard itself — a guided script that stands up a country's own database, applies all of this system's database structure to it, deploys the backend logic, and configures everything for that country's own domain and server.
  2. A "first account" bootstrap step — today every account must be invited by an existing administrator; a brand-new installation has no administrator yet, so the installer needs to safely create exactly one first account to get started.
  3. Verification on real self-hosted infrastructure — the system depends on several background-automation features of our current hosting provider (Supabase) that are assumed, but not yet confirmed, to work identically once a country is running its own copy. This needs a real test installation before being promised to a country as ready.

3.3 — What a country will need to provide / do

  • Its own server (a VPS or on-premises machine) and a domain name with an SSL certificate.
  • Someone with basic system-administration ability to run the guided installer and answer its prompts (technical, but not a software engineer).
  • An initial access request sent to the central team, so the very first administrator account for that country can be created.

3.4 — What "done" looks like

A country's own IT contact runs one guided installer end to end and finishes with a fully working, completely independent copy of this entire system — their own map, their own alerts, their own data, running on infrastructure they control. From that point on, the central team is not involved in their day-to-day operation at all; the country's own Country Admin invites and manages their own staff going forward, using the role system described above.

Recommended build order: (1) a trial self-host installation on a test server first, to confirm the assumptions in 3.2.3 above, before (2) building the first-account bootstrap step, then (3) building and testing the guided installer end to end, and only then (4) writing the step-by-step documentation — written last, so it describes what the installer actually does rather than the other way around.

4.Recent Feature Highlights

The most recently completed capabilities, in plain terms:

  • Cascading hazard risk — the system can now say "this earthquake also raises flood, epidemic, or landslide risk nearby," with every judgment traceable to an explicit, admin-editable rule (Section 2.3).
  • "How far does this reach" visualization — selecting any earthquake or wildfire on the map now shows a translucent circle sized to that event's real estimated impact radius (based on the earthquake's actual magnitude, or the wildfire's actual satellite-measured fire intensity), with a slider to explore "what if this had been stronger/weaker."
  • Distance-graded facility risk — schools, clinics, and emergency facilities near a selected hazard are now color-graded from yellow to red by how close they are to the epicenter, with an explicit on-screen note that this is a distance-based estimate, not a confirmed damage assessment.
  • Building density mapping — a new layer showing real building density per area (not just critical facilities), sourced from a global satellite-derived building dataset, for all three served countries.
  • Landslide-susceptibility mapping — steep-terrain zones (from real satellite elevation data) that meaningfully raise landslide risk after an earthquake, for all three served countries.
  • Category-filterable critical infrastructure — an operator can show/hide schools, health facilities, and emergency services independently (e.g. "it's nighttime, hide schools, show only health facilities").

6.Outstanding Items

6.1 — Internal, non-blocking (2 items)

Waiting on partner Module 039 — Risk & Scenario Modeling

One open question about whether a specific risk-index methodology (the INFORM index) should be adopted at the global/country level or with hand-curated sub-regional data, and whether that process repeats for every new country — this is waiting on a response from the UN partner team and cannot be resolved by engineering work alone.

Follow-up test Module 048 — Cascading Hazard Risk

A defense-in-depth security test (confirming a real, non-super-admin country administrator is correctly denied access to another country's cascade-risk configuration) has not yet been separately exercised with a live non-admin account — the same access-control pattern is already proven correct elsewhere in the system, so risk is assessed as low, but this is flagged for completeness.

7.Summary

The system's core mission — detect hazards in real time, understand their impact, and issue a compliant public alert — is fully built, tested, and running in production for three countries today, with 99.8% of all formally tracked engineering work complete. The only two items still open within the current scope are non-blocking and well understood. The next major initiative is not a missing feature but a deployment model change: giving each country its own fully independent, self-hosted copy of the same proven system.
